Running a self-hosted password vault, including the day someone gets locked out

Deployed a Vaultwarden server with mail delivery through Microsoft 365, and learned the hard way why the account recovery policy has to be enabled before anyone needs it.

Problem

Shared credentials were being passed around in chat messages and text files. A central vault was needed, self-hosted rather than cloud, with invitations and password resets working through the company mail system.

Approach

Deployment was straightforward. The interesting part came later: a colleague could no longer unlock his vault although he was sure the master password was correct. I had to work out what is actually recoverable in this architecture.

Solution

The vault is encrypted client side with the master password, so the server never holds anything that could decrypt it. Administrator recovery only exists if the account recovery policy was enabled beforehand and the user enrolled at that time. It had not been. The honest answer was that the personal vault was unrecoverable, while shared collection entries survived because they are encrypted to the organization key. I deleted and reinvited the account, and enabled the recovery policy for everyone else.

Result

One user lost personal entries. Nobody else will, because the policy is now active and enforced at enrollment.

What I learned

  • Understand the encryption model of a tool before you deploy it, not when a user is locked out.
  • Recovery policies are worthless retroactively. Enable them on day one.
  • Telling a user plainly that data is gone is better than three days of false hope.
