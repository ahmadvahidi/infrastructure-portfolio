A self-hosted VPN and the client that refused to connect

Set up a modern protocol VPN on a cloud server, then debugged a client rejection that had nothing to do with the configuration.

Problem

I needed a private, self-hosted VPN endpoint. The server side came up quickly, but the Android client rejected the connection with an unhelpful message while other clients worked.

Approach

Because the server accepted other clients, the problem had to be client side or version related. I compared what the server advertised against what the client supported.

Solution

The server was enforcing a minimum client version. The Android client in use was below it and was refused before any real handshake happened. Updating the client resolved it. Separately, the cloud provider's own firewall operates completely independently from the firewall inside the operating system, which is a recurring trap: a port can be open locally and still be unreachable.

Result

A working private VPN endpoint, and two debugging rules I now apply automatically.

What I learned

  • A cloud provider firewall and a host firewall are two separate walls. Opening one proves nothing about the other.
  • When one client fails and others work, compare versions before you compare configurations.
