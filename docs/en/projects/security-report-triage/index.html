Triaging a security report without creating panic

Five alerts on domain controllers and a Linux build runner, sorted into real findings, misconfigurations and false positives.

Problem

A generated security analysis landed on my desk listing pass the hash alerts on both domain controllers, a performance counter error, a virtualization tool error, low hardening scores and a full disk warning. Read literally, it looked like an active intrusion.

Approach

I worked through the findings one by one instead of reacting to the headline. For each alert the question was the same: what would this look like if it were normal behavior, and what would it look like if it were real.

Solution

The pass the hash alerts matched the pattern of ordinary directory replication between two domain controllers and were false positives from a detection rule that does not know which accounts are replication accounts. The disk warning on the build runner turned out to be transient, but investigating it surfaced a real finding: over a hundred pending updates including security patches. The virtualization error came from an incompletely removed toolset left over from an earlier platform migration, on a machine that no longer runs on that platform at all. The hardening scores were genuine and became a separate backlog item.

Result

Two false positives closed with an explanation, two real findings scheduled, and no emergency reboot of a domain controller on a Monday morning. The remediation was moved to the regular maintenance window later in the week.

What I learned

  • A detection rule that does not know your environment will call your replication traffic an attack. Tune it or document it.
  • Refusing to reboot a domain controller at the start of the week is a technical decision, not procrastination.
  • Leftovers from an old migration keep generating alerts for years. Removal is part of migration, not a nice to have.
