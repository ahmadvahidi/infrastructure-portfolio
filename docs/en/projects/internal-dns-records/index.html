Publishing two new internal portals via DNS

Two new hostnames pointing at an existing web server, created as aliases, verified end to end, and documented with a rollback path.

Problem

Two new internal portals needed their own hostnames. The web server bindings already existed, so only name resolution was missing.

Approach

First verify the target: confirm the web server resolves to the expected address in both directions, and check which ports actually respond. Then decide between a direct address record and an alias record. I chose aliases so that if the web server ever moves, one record changes instead of several.

Solution

Two alias records created via PowerShell, after discovering the DNS module was not available on the first machine and switching to one where it was. Verified in the management console, in the subdomain node, and with a real HTTP request returning a success status.

Result

Both portals reachable by name, existing records untouched, and a written runbook covering the decision rationale, the commands, the interface steps and the rollback.

What I learned

  • Alias records over address records when several names point at one host. It turns a future migration into a one line change.
  • Verify the target before creating the record. A name pointing at something that does not answer is worse than no name.
  • Write the rollback command in the runbook while you still remember what you changed.
