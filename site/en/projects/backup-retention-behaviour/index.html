Why the backup count exceeds the retention limit

A retention rule set to 28 backups showed 29. Explaining why, and confirming that no emergency action was needed.

Problem

A server's backup plan was configured to keep 28 recovery points, but the console showed 29. With limited free storage, the fear was that the next run would create a new full backup and fill the disk.

Approach

I worked through how the retention mechanism actually behaves rather than trusting the number in the interface.

Solution

Backup software intentionally exceeds the retention limit when dependent incremental points cannot be deleted without breaking the chain, and cleanup runs after the new backup completes rather than before. A temporary overage is expected behavior. A new full backup is only triggered by specific events such as changing the format, destination or encryption, adding a source disk, or recreating the plan. None applied, so the next run was incremental.

Result

No emergency intervention, and a documented method for estimating daily storage consumption and remaining runway by comparing archive sizes on consecutive days.

What I learned

  • Cleanup after the backup, not before, means free space must cover the overage. Size storage for the peak, not the average.
  • Never delete archive files by hand. It breaks the chain and silently invalidates every recovery point that depends on it.
  • If storage is the real constraint, switch retention from a count to a size limit.
