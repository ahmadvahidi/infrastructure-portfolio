Turning an IP spreadsheet into a real address management database

14 networks, 11 VLANs and 248 host records imported, including the cleanup of 98 hostnames that no system would accept.

Problem

The IP address plan was a spreadsheet with twelve sheets, inconsistent naming and hidden structure. One sheet turned out to contain three separate network blocks rather than one, which is exactly the kind of thing a spreadsheet lets you get away with.

Approach

I analyzed the source structure first and only then wrote the import. Data quality problems were documented rather than silently corrected, because silently fixing someone else's data is how you lose the audit trail.

Solution

The import produced 11 VLANs, 13 IP networks, 248 host name objects and 248 address objects. 98 hostnames had to be sanitized because the target system validates them as DNS names and rejects spaces, underscores and dots. Genuine fully qualified names were split correctly into host and domain parts. Four data quality issues were flagged with a review prefix in the comment field instead of being guessed at.

Result

A queryable address database instead of a spreadsheet, with the known bad records visibly marked for review.

What I learned

  • Analyze the source before writing the importer. Spreadsheets hide structure that no schema would allow.
  • Flag bad data, do not fix it silently. The person who created it is the only one who knows what it was supposed to say.
  • Systems that validate names as DNS names will reject a large part of any hand maintained list. Plan for the sanitization step.
