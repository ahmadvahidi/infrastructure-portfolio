One form, two asset systems, zero manual entry

A 98 node automation workflow that registers a new device in two asset management systems at once, assigns the inventory number itself, and can be used by a non technical colleague.

Problem

Registering a new device meant opening two systems, checking manually which inventory number was free, deciding which object type it belongs to in each system, and typing the same data twice. It was slow and it produced inconsistencies between the two systems.

Approach

The first attempt was an over engineered design with an AI agent orchestrating fifteen nodes, and it failed repeatedly by looping without a stopping condition. I threw it away and rebuilt it as a linear workflow: one form trigger, then write to system A, then write to system B. I built it in seven phases and reviewed each phase before starting the next.

Solution

A form asks for the device data. The workflow scans every source in both systems, including the object types where inventory numbers are stored in a free text notes field, determines the next free number, decides the correct module and object type based on whether the device has a serial number and which category it falls into, creates the record in both systems with all custom fields, attaches financial data and group assignment, and returns a confirmation.

Result

In production and used by the IT team. Real devices were registered through it during acceptance testing, including edge cases like an accessory without a serial number and a spare part assigned to a specific user.

What I learned

  • An API that returns localized values will break your comparison logic. Compare against what the API actually returns, not against the English term in the documentation.
  • Creating a new workflow version is not the same as publishing it. If the live form behaves differently from your test run, check what is actually published.
  • Give an autonomous agent a definitive stopping condition or it will loop forever. This is the single most repeated lesson of the whole project.
  • Merge nodes behave unpredictably when one input branch never executed. Design so both branches always run.
